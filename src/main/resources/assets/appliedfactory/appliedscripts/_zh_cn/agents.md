你正通过 MCP 操作一台 Minecraft **Applied Factory** 控制器。你可以对控制器运行 TypeScript 探测程序、读取日志、反复迭代，最后上传正式程序。工厂是真实存在的：网络、机器、资源与配方都存在于世界中，行为与 Minecraft + Applied Energistics 2 一致。
下文与 API 文档中的 “bus” 指 “Factory Bus（工厂总线）”，这是本模组添加的一种 AE2 部件，用作世界执行器、交互器与 I/O 端点。可用能力定义在文档的 “Bus” 对象上。

## 工具

- `appliedfactory_status` — 只读状态（连接、MCP 服务端口、已绑定控制器坐标及其当前脚本文件、`workspace` 路径、自动重载开关）。
- `appliedfactory_execute` — 运行探测程序；返回 `logs` + `result` + `reason`。主要工具。
- `appliedfactory_upload` — 从真实的工作区 `file` 编译并替换控制器的正式程序（编译检查；失败时原程序保持不变）。上传必须提供本地文件，以便控制器 GUI 保留可编辑的备份。

如果这些工具不存在，请确认：1、玩家已正确安装模组并在 gui 里连接了 mcp。 2、控制器所在的区块被加载且游戏未暂停 3、你所使用的 agent 框架正确配置了项目级 mcp。

如果未配置项目级 mcp，提醒用户针对你的 agent 框架进行配置。端点为`http://127.0.0.1:39291/mcp`；修改 MCP 配置后需重启 agent。

## 重要说明
- API 参考位于本文件夹（`SCRIPT_API.md`）。
- 允许并鼓励为实验性生产搬运资源。
- 日志输出上限：单条日志 16,000 字符，所有日志合计 120,000 字符，`result` 40,000 字符，40 条 pending。
- 在 AE2 中，只要加工样板输出表的全部资源回到下单网络（无论从何处返还），该加工即视为成功。为简化流程，最好只在处理函数中负责推送，而在被动工作流中拉取产物。
- 多步加工最好拆成独立样板，让 AE2 来组织生产。
- 频繁处理小样板会消耗大量 I/O 时间，因此对于高频样板最好倍增其输入输出，提高并行吞吐量。
- 用 `require_recipes(spec)` 批量请求配方。一般 JSON 数据可用相对默认导入，例如 `import data from "./data.json"`；不支持导入 TypeScript/JavaScript 模块。
- 如果需要烘培配方，留下可复用的烘培脚本 —— 例如产出所导入 JSON 的小生成器，以便整合包更新后能重新生成数据。
- 大多数机器只输出产物，这意味着可以不加过滤地直接提取，也不会将正在处理的输入取出；这些输入仍可通过 `storage()` 查看。
- `ResourceChannel` 的所有合法值都能被样板处理器处理，因为某些附属模组已将其注册为可用频道。
- 空资源与空 ResourceArray 可以安全传输（no-op），因此无需额外检查。
- 包含大量原料的网络很可能是下单网络，只有机器的很可能是生产网络；
- 下单网络可能包含多种资源，尽量不要把它们全部列出来。
- 整合包可能修改配方，请相信导出的数据而非你的记忆。
- 不同的控制器与网络结构基本上意味着多条生产线，不要把它们当作一个并合并处理流程。
- 如果用户未提及，不需要文件夹之外的信息。若出现 决策信息不足/实现路径不明确/合成所需条件不具备 的情况，**不要自行拓展检查范围而是询问用户**，用户比你更熟悉游戏与流程。
- 值得询问用户的情况包括但不限于：1、合成触发方式（自动触发、红石触发等） 2、是否需要被动资源（如能源、某种固定消耗的流体或物品） 3、机器是否仅输出产物（决定是否要加过滤） 4、是否进行试生产，生产什么东西。 5、是否需要倍增样板
